Architecture

Each simulation runs in its own JVM: the original code keeps static state and reads/writes the relative folder src/others/.

How to demonstrate

  1. Reproduction: run the authors' unmodified NASA experiment and show the byte-identity check against the outputs they committed.
  2. Budget guard: set a budget (₹) and a response-time target, run original vs guarded, read the explanations and warnings.
  3. Workloads & forecast: upload a CSV (or pick a sample), inspect forecast, spikes, warnings and capacity/cost, then replay it in AutoScaleSim.
  4. History: every run and upload is stored in the database and can be reopened.

1 · Reproduction of the original experiment

Runs the authors' autoscalesim.ExperimentalSetup.main() without changes (NASA trace, 7 days, SLA-aware rule, t2.medium) and compares the produced monitoring files with the ones the authors committed to their repository.

About 10 seconds.

Comparison with the paper

2 · Budget-aware, explainable auto-scaling

The original planner decides first; the guard then checks the decision against a paced budget (the simulator's own billing rule: ceil(hours) × US$0.04 per t2.medium hour), explains it, and warns when the budget and the response-time target cannot both be met.

Three real simulations, about 20 seconds.

Budget sweep (evaluation)

One original run + one guarded run per budget.

3 · Custom workloads and predictive spike warnings

Upload per-minute request counts (minute,requests) or a request log (timestamp column). The forecast is Holt-Winters exponential smoothing with a daily season, chosen by grid search; spikes are buckets above the trailing 2-hour mean + k·σ; warnings fire when the forecast's upper bound crosses that threshold ahead of time. One-off bursts of up to an hour are kept out of the trend and daily season, so a single spike is not predicted again.

Upload a workload CSV

Limits: 120 minutes to 7 days, at most 2000 requests per minute, 20 MB. Stored in the database.
